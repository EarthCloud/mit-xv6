## 14. 中断时的危险

一些xv6自旋锁保护线程和中断处理程序共用的数据。

例如，`clockintr`定时器中断处理程序在增加`ticks`(**_kernel/trap.c_**:163)的同时内核线程可能在`sys_sleep`(**_kernel/sysproc.c_**:64)中读取`ticks`。锁`tickslock`串行化这两个访问。

自旋锁和中断的交互引发了潜在的危险。中断发生的时刻是不确定的，这也就意味着，获得锁的顺序可能是不确定的。假设`sys_sleep`持有`tickslock`，并且它的CPU被计时器中断中断。`clockintr`会尝试获取`tickslock`，意识到它被持有后等待释放。在这种情况下，`tickslock`永远不会被释放：只有`sys_sleep`可以释放它，但是`sys_sleep`直到`clockintr`返回前不能继续运行。所以CPU会死锁，任何需要锁的代码也会冻结。

## 15. 处理方案

为了避免这种情况，如果一个自旋锁被中断处理程序所使用，那么CPU必须保证在启用中断的情况下永远不能持有该锁。

Xv6更保守：当CPU获取任何锁时，xv6总是禁用该CPU上的中断。中断仍然可能发生在其他CPU上，此时中断的`acquire`可以等待线程释放自旋锁；由于不在同一CPU上，不会造成死锁。

当CPU未持有自旋锁时，xv6重新启用中断；它必须做一些记录来处理嵌套的临界区域。`acquire`调用`push_off` (**_kernel/spinlock.c_**:89) 并且`release`调用`pop_off` (**_kernel/spinlock.c_**:100)来跟踪当前CPU上锁的嵌套级别。当计数达到零时，`pop_off`恢复最外层临界区域开始时存在的中断使能状态。`intr_off`和`intr_on`函数执行RISC-V指令分别用来禁用和启用中断。

### 如果不用 `push_off/pop_off` 会怎样？

首先我们要明确一个大前提：**在 xv6 中，获取自旋锁的第一步，必须是关闭当前 CPU 核心的中断。** 为什么？因为如果你拿了锁，刚好时钟中断来了，CPU 去执行中断处理程序，而中断处理程序恰好又要去拿这把锁……此时原进程被挂起无法释放锁，中断程序又在死等这把锁，**“单核死锁（Local Deadlock）”** 当场发生！

假设我们不用 `push/pop`，只用最简单的 `intr_off()`（关中断）和 `intr_on()`（开中断）来写锁逻辑：

```c
// 极其简陋且有 Bug 的锁
void bad_acquire(lock *lk) {
    intr_off(); // 关中断！
    // ... 拿锁逻辑 ...
}

void bad_release(lock *lk) {
    // ... 释放锁逻辑 ...
    intr_on();  // 开中断！
}
```

现在，假设代码需要同时修改两个复杂的数据结构，于是它连续拿了两把锁：

1. 代码调用 `bad_acquire(&Lock_A)`：中断被关闭。安全。
2. 代码调用 `bad_acquire(&Lock_B)`：中断再次被关闭。安全。
3. **灾难发生：** 代码执行完毕，准备释放，调用 `bad_release(&Lock_B)`。
4. `bad_release` 释放了 B 锁，然后执行了 `intr_on()` 打开中断。
5. 但是此时进程还持有 Lock_A，中断开启后，如果发生时钟中断，单核死锁瞬间爆发。

简单的开关中断，无法处理**嵌套锁（Nested Locks）**。内核需要记住是什么时候关的中断，并且只有在最后一把锁被释放时，才能重新打开中断。

为了解决嵌套问题，xv6 给每个 CPU 核心（`mycpu()` 结构体）配备了两个极其关键的变量：

- **`noff` (Number of off)：** 记录当前 CPU 拿了多少把锁（嵌套深度）。
- **`intena` (Interrupt Enable)：** 记录在拿**第一把锁之前**，CPU 的中断到底开没开。
    

这就像是一个专门为中断状态设计的**栈（Stack）**。

#### 1. `push_off` (进栈：获取锁时调用)
```c
void push_off(void) {
  int old = intr_get(); // 读一下当前真实的硬件中断状态
  intr_off();           // 毫不犹豫，立刻关掉硬件中断
  
  if(mycpu()->noff == 0)      // 如果这是我们拿的【第一把锁】
    mycpu()->intena = old;    // 把刚才读到的真实状态存进 intena 里当备份
    
  mycpu()->noff += 1;         // 嵌套深度 +1
}
```

**它的核心逻辑是：** 先关中断。但我只在拿**第一把锁**的时候（`noff == 0`），记住当时的硬件状态。后面拿第二把、第三把锁时，只加嵌套深度（`noff++`），不再覆盖备份。

#### 2. `pop_off` (出栈：释放锁时调用)

```c
void pop_off(void) {
  struct cpu *c = mycpu();
  c->noff -= 1;               // 嵌套深度 -1
  
  if(c->noff == 0 && c->intena) // 如果这是我们要释放的【最后一把锁】，并且最开始中断是开着的
    intr_on();                  // 终于可以安全地重新打开硬件中断了！
}
```

 释放锁时，先减嵌套深度。只要 `noff` 还没变成 0，说明手里还有别的锁，**绝对不准开中断**。只有当所有的锁都释放完（`noff == 0`），并且我翻看之前的备份记录（`intena`），发现最开始中断是开着的，我才真正调用 `intr_on()` 恢复它。
