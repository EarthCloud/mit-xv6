## 6. 加锁与并行性间的矛盾

加锁主要是为了出于正确性的利益而抑制并行性 。因为性能也很重要，内核设计者经常需要思考如何以既能实现正确性又能获得良好并行性的方式使用锁 。虽然 xv6 并非系统性地为高性能而设计，但仍然值得考虑哪些 xv6 操作可以并行执行，以及哪些可能会在锁上发生冲突 。

xv6 中的管道是并行性相当好的一个例子 。每个管道都有自己的锁，以便不同进程可以在不同的 CPU 上并行读写不同的管道 。然而，对于给定的一个管道，写入者和读取者必须等待彼此释放锁 ；他们不能同时读写同一个管道 。同样，从空管道读取（或向满管道写入）必然阻塞，但这并不是加锁方案造成的 。

上下文切换是一个更复杂的例子。两个各自在自己 CPU 上执行的内核线程可以同时调用 `yield`、`sched` 和 `swtch`，并且这些调用将并行执行 。这两个线程分别持有一个锁，但它们是不同的锁，因此不必彼此等待 。然而，一旦进入 `scheduler`，这两个 CPU 在搜索进程表中寻找处于 `RUNNABLE` 状态的进程时可能会在锁上发生冲突 。也就是说，xv6 很可能在上下文切换期间从多个 CPU 中获得性能收益，但或许并未达到其最大潜力 。

另一个例子是不同进程在不同 CPU 上对 `fork` 的并发调用 。这些调用可能需要为了 `pid_lock` 和 `kmem.` `lock`，以及为了在进程表中搜索一个 `UNUSED` 进程所需的特定于每个进程的锁而互相等待 。另一方面，两个执行 `fork` 的进程可以完全并行地复制用户内存页面并格式化页表页面 。

在上述的每个例子中，加锁方案在某些情况下都**牺牲了并行性能** 。在每种情况下，**都可以通过使用更精细的设计来获得更多的并行性**。这是否值得取决于细节：相关操作被调用的频率有多高，相关代码在持有一个竞争锁时花费了多少时间，可能有多少个 CPU 同时运行发生冲突的操作，以及代码的其他部分是否构成了更具限制性的瓶颈 。很难凭空猜测给定的加锁方案是否会引发性能问题，或者新设计是否能显著改善性能，因此通常需要在**真实工作负载**下进行实际测量 。
