## 1. 锁面临的挑战

缓存项通常是加锁的挑战。例如，文件系统的块缓存 (kernel/bio.c:26) 存储了最多 NBUF 个磁盘块的副本 。至关重要的是，一个给定的磁盘块在缓存中最多只能有一个副本 ；否则，不同的进程可能会对本应是同一数据块的不同副本进行冲突性的修改 。每个缓存块都存储在一个 `struct buf` 中 (kernel/buf.h:1) 。`struct buf` 有一个 `lock` 字段，这有助于确保一次只有一个进程使用给定的磁盘块 。

但是，仅有这个锁是不够的：如果一个块根本不在缓存中，而两个进程同时想要使用它该怎么办 ？此时并不存在 `struct buf`（因为块还没有被缓存），因此也就没有什么可以加锁的 。Xv6 处理这种情况的方法是，将一个额外的锁 (`bcache.lock`) 与缓存块标识集合关联起来 。需要检查一个块是否被缓存的代码（例如 `bget` (kernel/bio.c:59)），或者改变缓存块集合的代码，必须持有 `bcache.lock` ；在代码找到它需要的块和 `struct buf` 之后，它可以释放 `bcache.lock` 并仅锁定那个特定的块 。这是一个常见的模式：一个锁用于管理集合，另外每个项目各有一个锁 。

## 2. 锁的获取释放序列

通常，获取锁的同一个函数也会负责释放它 。但更准确的看法是，**锁在一个必须表现为原子的操作序列开始时被获取，并在该序列结束时被释放** 。如果这个序列在不同的函数、不同的线程或不同的 CPU 上开始和结束，那么锁的获取和释放也必须保持这种跨度 。锁的作用是强制其他使用者等待，而不是将一段数据绑定到特定的执行代理上 。一个例子是 `yield` (kernel/proc.c:515) 中的 `acquire`，它在调度器线程中被释放，而不是在获取它的进程中被释放 。另一个例子是 `ilock` (kernel/fs.c:289) 中的 `acquiresleep`；这段代码在读取磁盘时经常会进入休眠状态 ；它可能会在不同的 CPU 上被唤醒，这意味着该锁可能在不同的 CPU 上被获取和释放 。

释放一个受嵌入其内部的锁保护的对象是一件微妙的事情，因为仅仅拥有该锁不足以保证释放操作是正确的。当某些其他线程正在 `acquire` 中等待使用该对象时，问题就出现了；释放对象会隐式地释放其中嵌入的锁，这将导致等待中的线程发生故障。一种解决方案是跟踪该对象存在的引用数量，以便它仅在最后一个引用消失时才被释放。请参阅 `pipeclose` (kernel/pipe.c:59) 以获取示例；`pi->readopen` 和 `pi->writeopen` 跟踪管道是否还有指向它的文件描述符。

```c
void

pipeclose(struct pipe *pi, int writable)

{

  acquire(&pi->lock);

  if(writable) {

    pi->writeopen = 0;

    wakeup(&pi->nread);

  } else {

    pi->readopen = 0;

    wakeup(&pi->nwrite);

  }

  if(pi->readopen == 0 && pi->writeopen == 0) {

    release(&pi->lock);

    kfree((char *)pi);

  } else

    release(&pi->lock);

}
```
